三问题分析

谓词对 order_date 左列施加函数（DATE()），优化器无法利用 idx_tenant_created(tenant_id, created_at) 形成范围扫描，回退为全表扫描；扫描 126 万行仅返回约 400 行（3150:1）。当前没有证据表明需要扩容——瓶颈在访问路径，不在资源。

四变更建议 规则 + 确定性估算
变更操作在隔离环境验证复合索引候选：CREATE INDEX idx_tenant_status_created ON orders(tenant_id, status, created_at); 并对比新旧计划的扫描行数与 P95。
风险提示TiDB 在线 DDL，不阻塞读写；写入期间有写放大与临时空间开销，建议业务低峰执行；索引写入路径将承担 1 次/行的额外写入成本。
成本预估预计 15~30 秒（126 万行 × 约 32B/行 ≈ 40MB 索引存储；构建速率按 5 万行/秒保守档）。公式：行数 ÷ 保守构建速率；存储 = Σ索引列字节宽 × 行数 × 1.5
收益预估扫描行数 126 万 → 约 842 行（-99.9%，按过滤基数估算）；P95 预估 2.8s → < 0.5s。公式：索引后扫描 ≈ 返回行数 × 回表系数；同构真实 A/B 实测（2026-09-03 TiDB v8.5.8 证据包）：65,537 keys → 2 keys，P95 66ms → 4ms
五验证方法

隔离环境对相同参数分布运行普通 EXPLAIN 与压测：确认访问方式由 TableFullScan 变为 IndexRangeScan；扫描行数下降 ≥ 90%、P95 < 500ms、写入回归 ≤ 5% 为达标。

一结论 P2规则确认 · 真实证据

同一 SQL Digest 在一分钟窗口内 执行 20 次，每次全表扫描 65,537 keys，加权扫描量 1,310,740 keys；属于高频重复扫描（热点重复），单次延迟不高但累计消耗显著。P2 判定：p95 66ms 未达 5s 阈值；若生产窗口 p95 ≥ 5s 且执行 ≥ 20 次将自动升 P1。

三问题分析

该 SQL 单次执行仅 66ms（p95），但访问路径为全表扫描（每次 65,537 keys），且被应用以循环方式高频调用（典型 N+1 模式）：同一分钟窗口 20 次，加权扫描 131 万 keys。延迟问题不大，但重复扫描放大 CPU/IO 消耗，且随业务量线性恶化。

四变更建议 规则 + 实测参考
变更操作应用层把循环单条查询合并为批量查询：SELECT ... FROM index_orders WHERE customer_id IN (?, ?, ...) AND state=?（或复用 Prepared Statement 连接）；可选配合索引 idx_customer_state(customer_id, state) 消除全表扫描。
风险提示应用代码改动，需业务方确认批量语义一致（返回顺序、空集处理）；批量上限控制参数数量，防语句超长。
成本预估预计 1~2 个研发工时（代码改动 + 回归测试）；若仅加索引则 15~30 秒在线 DDL。公式：工时估算按改动点数量（循环调用点 1 处 + 测试）；索引成本同样例一公式
收益预估扫描量 -75%（实测，20→5 次调用）；若合并为 1 次批量查询 + 索引，预估 -95%。依据：真实证据包 17-repeated-scan 实测 1,310,740 → 327,685 keys
五验证方法

改造后在同等窗口对比 Statement Summary 的 exec_count 与加权 keys：目标窗口加权扫描量下降 ≥ 75%，且单次 P95 不回退；业务回归测试确认结果集一致。

六回滚步骤

应用代码回滚到原循环查询版本即可（无 DDL 变更时零数据风险）；如已加索引，DROP INDEX idx_customer_state;。
