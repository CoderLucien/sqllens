# SQLLens 中文主文档设计

## 目标

将 GitHub 仓库中的人工阅读文档统一整理为中文主文档，让产品、研发、测试和外部贡献者能够直接用中文理解项目定位、架构决策、安全边界、开发流程与发布要求。

本次只调整文档表达和导航，不改变产品行为、接口契约、构建流程或当前发布候选。

## 范围

以下内容就地中文化：

- 根目录 `README.md`；
- `AGENTS.md`；
- `docs/adr/*.md`；
- `docs/contracts/README.md`；
- `docs/superpowers/plans/*.md`；
- `docs/superpowers/specs/*.md`；
- `docs/threat-model.md`；
- `tasks/*.md`。

当前基线共有 16 份 Markdown；加入本设计文档和根 README 后，目标集合共 18 份 Markdown。

## 不在范围内

- Apache `LICENSE` 保留官方英文原文，避免法律含义因翻译变化；
- JSON Schema、JSON 示例、Python、Shell、TypeScript、YAML、Dockerfile 等机器读取内容不翻译；
- API 路径、字段名、状态值、环境变量、命令、文件路径、代码标识符和哈希不翻译；
- 不为每份中文文档额外维护英文镜像，避免双份内容长期漂移；
- 不把本次文档提交并入正在验证的 Layer 1 RC。

## 信息架构

根 README 作为仓库入口，按以下顺序组织：

1. 产品定位与 P0 能力；
2. 当前交付边界和安全承诺；
3. 快速开始与常用命令；
4. 仓库结构；
5. 架构决策、契约、威胁模型和实施计划导航；
6. 测试、发布与贡献约束。

现有 ADR、规格、计划和任务文件保留原文件名与编号，避免破坏文件级历史链接。标题和正文改为中文；如标题变化影响文档内锚点引用，则同步更新对应链接。技术名词在首次出现时采用“中文名称（English Term）”，后续优先使用统一中文名称。

## 翻译规则

- 保持事实、约束、风险等级和验收标准不变，不做产品能力扩写；
- 代码块内容原则上逐字保留，代码块外的解释改为中文；
- 行内代码中的命令、路径、字段、状态值和符号逐字保留；
- `MUST`、`SHOULD`、`MAY` 等规范词分别统一为“必须”“应当”“可以”；
- `active`、`staged`、`pending` 等状态值保留英文并使用行内代码格式；
- SQLLens、TiDB、Prometheus、Plan Replayer、Diagnosis Case 等产品或协议名称保持原名；
- 对无法准确对应的安全术语，使用中文解释并在首次出现时保留英文原词。

## 分支与提交策略

文档工作在独立分支 `docs/chinese-documentation` 上完成，基线为 `0cfb7374104b77e89248b27cf18dfc2ca2a84661`。

按三个可审查批次提交：

1. 根 README、`AGENTS.md` 与 `tasks/*.md`；
2. ADR 与威胁模型；
3. 契约说明、设计规格与实施计划。

每个批次只包含文档变更，便于逐批审查和回退。分支可先推送 GitHub；只有在当前 RC 结束后，才评估并入正式 `main`。

## 验收方式

每个批次必须满足：

- 目标 Markdown 已包含中文正文，不留整段英文叙述；
- 文件名和 ADR 编号保持不变，内部相对链接与锚点引用均有效；
- 代码块数量与类型没有意外变化；
- 命令、路径、API 字段、状态值和哈希没有被翻译或改写；
- 文档中的产品边界与现有代码、测试和任务门禁一致；
- `git diff --check` 通过，工作树无非文档改动。

最终检查还包括 Markdown 文件清单、内部相对链接、中文覆盖率和提交范围核对。

## 风险与控制

- **术语漂移**：先冻结术语规则，再按批次翻译并交叉检查。
- **命令被误改**：代码块和行内代码单独核对，机器标识保持原文。
- **历史链接失效**：不重命名现有文件，不更改 ADR 编号。
- **文档超前于实现**：只翻译当前事实，不新增未实现能力；不确定项继续标记为未验证或后续工作。
- **影响发布候选**：文档分支与 RC 工作树隔离，当前候选和三件套不包含本次变更。
